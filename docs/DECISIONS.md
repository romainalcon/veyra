# Veyra — Architecture decision log

## ADR-001 — Name
**Decision:** Veyra replaces the working name Pulse.

## ADR-002 — Database
**Decision:** MariaDB 11.4+ replaces PostgreSQL. V1 uses ordinary indexed history tables with batched retention, not PostgreSQL-style partitions.

## ADR-003 — Probe runtime
**Decision:** All probes run in Laravel Horizon workers. No mandatory external agent, microservice or separate language runtime.

## ADR-004 — Deployment
**Decision:** Docker Compose for public Community distribution; Vito Deploy for private installations. Same application code.

## ADR-005 — Open Core
**Decision:** Community core and optional Cloud extensions share a codebase but have explicit interfaces. The Community core is licensed under **AGPL-3.0-only** (confirmed for the 1.0.0 release, source at https://github.com/romainalcon/veyra); optional Cloud modules under `extensions/cloud` may use a separate commercial license. A contribution policy (DCO or CLA) must be defined before accepting external contributions, and trademark/domain availability for "Veyra" still needs verification.

## ADR-006 — Scheduling reliability
**Decision:** MariaDB-backed atomic scheduling and outbox; idempotent Horizon jobs and ordered state transitions.

## ADR-007 — Authentication and UI foundation
**Decision:** Adapt the official Laravel Vue starter kit (Fortify headless auth, shadcn-vue on reka-ui, Wayfinder typed routes) on **Inertia 3** instead of Inertia 2. Two-factor auth, passkeys, `laravel/chisel` and `vite-plus` are removed; standard Vite 8, ESLint and Prettier are used. Fortify actions live in `app/Domain/Identity`.
**Why:** Maintained, conventional code paths for auth; Inertia 3 is the current major used by the kit (layout props, built-in HTTP client).

## ADR-008 — Tenant resolution through the URL
**Decision:** Tenant routes are prefixed `/o/{organization:slug}`. `ResolveOrganization` requires membership and answers **404** for non-members. Child resources use scoped route bindings; policies re-check organization ownership. The last visited organization is kept in session only as a redirect hint.
**Why:** Explicit tenant context, safe across browser tabs, shareable links, no hidden "current organization" state.

## ADR-009 — UUIDv7 identifiers for users
**Decision:** `users` and all organization tables use UUIDv7 primary keys stored as `CHAR(36)` (`HasUuids`). Slugs are immutable after creation.
**Why:** Consistency with business entities, no sequential ID enumeration. Binary storage only if benchmarks justify it.

## ADR-010 — Fixed roles as an enum
**Decision:** Owner/Admin/Member/Viewer are a PHP enum with capability methods, enforced by `OrganizationPolicy`. No permission package. Invariant: an organization always keeps at least one owner (owner rows locked with `SELECT … FOR UPDATE`).
**Why:** Four fixed V1 roles do not justify a dynamic permission system.

## ADR-011 — Edition boundary
**Decision:** `config('veyra.edition')` identifies the edition (`community` by default). No Cloud code or entitlement interface is introduced in Sprint 1; the first real entitlement (e.g. monitor limits) will add an explicit contract with a Community implementation, and Cloud modules will live under `extensions/cloud`.
**Why:** Avoid speculative abstractions while keeping the boundary documented.

## ADR-012 — Invitations
**Decision:** Pending invitations store only a SHA-256 hash of a 64-character random token, expire after `VEYRA_INVITATION_TTL_HOURS` (default 168), are unique per (organization, e-mail) and are deleted when accepted or revoked. Acceptance locks the row, requires a verified account with the invited e-mail. The invitation mail is queued encrypted on `notifications`. When public registration is disabled (`VEYRA_REGISTRATION_ENABLED=false`), only invited e-mails may register.

## ADR-013 — SSRF strategy and private networks
**Decision:** Validate scheme, port, every DNS answer and every redirect hop in the application (`DestinationGuard`), pin the connection to the validated IP with `CURLOPT_RESOLVE`, follow redirects manually and ignore environment proxies. Private networks are reachable only through the instance-level opt-in `VEYRA_PROBES_ALLOW_PRIVATE_NETWORKS` (forced off on Cloud); loopback, link-local and metadata endpoints are never reachable.
**Why:** Self-hosted users legitimately monitor internal services, while the default and Cloud must not allow internal scanning. Network egress filtering remains required in addition.

## ADR-014 — Scheduling outbox and catch-up rules
**Decision:** Due monitors are claimed with `SKIP LOCKED` into `monitor_dispatches` in the same transaction that advances `next_check_at`; a relay publishes rows to Redis and redelivers stale ones (3 attempts max). Missed slots are skipped, stale dispatches are marked `skipped`, and no check is recorded in either case.
**Why:** MariaDB stays the source of truth; Redis loss or worker outages cannot lose schedules or fabricate failures ("missing data is UNKNOWN, never DOWN").

## ADR-015 — Confirmed state semantics
**Decision:** States are recomputed from the latest checks under a row lock (no incremental counters). DEGRADED means 1–2 unconfirmed failures and never opens an incident; DOWN needs 3 consecutive failures, recovery 2 consecutive successes (configurable per instance). Missing data yields UNKNOWN and never opens or resolves an incident.
**Why:** Idempotent, order-safe transitions, and a worker outage can never masquerade as service downtime.

## ADR-016 — Real-time by identifiers
**Decision:** Reverb events contain only identifiers; pages reload their props over HTTP (debounced), resync after reconnection and fall back to 30 s polling while disconnected.
**Why:** Reverb stays a delivery mechanism; authorization and data shaping remain in HTTP controllers.

## ADR-017 — Idempotent notification delivery
**Decision:** Domain events create delivery rows keyed by (incident, channel, event); a unique queued job sends each row with bounded, exponential retries and distinguishes transient from permanent failures. Mail is sent synchronously inside that job (no second queue hop).
**Why:** Replayed events, duplicate jobs and worker restarts must never spam, and every delivery outcome must be visible.

## ADR-018 — Charts with shadcn-vue Charts (@unovis)
**Decision:** Add `@unovis/vue` and `@unovis/ts` (pinned to 1.8.1) with the shadcn-vue `chart` components (copied from the official registry, adapted to direct `@unovis` subpath imports) for latency and incident charts; uptime bars are plain styled elements.
**Why:** Consistent with the shadcn-vue UI and themes, without hand-writing axes, tooltips and crosshairs. The shadcn-vue CLI requires Node 22, so the registry files were reviewed and added manually.

## ADR-019 — Uptime over observed checks with explicit coverage
**Decision:** Uptime is computed only over observed checks; coverage (observed ÷ expected) is reported alongside, and periods without data are "No data".
**Why:** A worker or scheduler outage must not masquerade as downtime nor inflate uptime to 100 %.

## ADR-020 — Release operations
**Decision:** `/health` (public status, token-protected details), a scheduler heartbeat and a "monitoring paused" banner expose worker/scheduler outages explicitly; `veyra:doctor` validates production configuration; backups are logical MariaDB dumps plus the APP_KEY; images are published to GHCR on `vX.Y.Z` tags with provenance and SBOM; the Docker stack is smoke-tested and backup/restore-drilled in CI.
**Why:** The V1 acceptance requires that a probe-worker outage never masquerades as downtime and that a clean install can be operated and restored without manual knowledge.

## ADR-021 — Planned maintenance: probe and flag
**Decision:** One-off maintenance windows (UTC, `[starts_at, ends_at)`, at most `VEYRA_MAINTENANCE_MAX_HOURS`, default 168) keep probing their monitors. Checks are flagged `in_maintenance` from their scheduled slot; while the newest check is flagged (or a window is running) the confirmed state is `MAINTENANCE`, which never opens, resolves or confirms an incident and suppresses reminders. Flagged checks are excluded from uptime, coverage, expected checks and latency. When the window ends the state becomes `UNKNOWN` with streaks restarting from the window end, exactly as after a resume. `veyra:maintenance:transition` (every minute) applies entries and exits on time under the `monitor_states` row lock. A started window keeps its start; only future windows can be cancelled, running ones are ended early. Recurring windows are deferred.
**Why:** Operators see when a service comes back, history stays truthful, and planned work neither alerts nor degrades uptime; results from before a window can never confirm an outage after it.

## ADR-022 — Public status pages: whitelisted, sessionless snapshot
**Decision:** Status pages are served at `/status/{slug}` (global unique slug, reserved words refused) by a route without the `web` middleware group: no session, no cookies, no CSRF, and a dedicated Inertia middleware sharing only the instance name, version and source link. The payload is built by `StatusPageSnapshot` from a whitelist (public display names, public statuses, 90-day uptime, public incident updates, maintenance title/description) and cached 30 s; monitor identifiers, names, URLs, causes, error codes and internal notes never leave the server; incidents, updates and windows are keyed by per-page HMACs. `UNKNOWN` is shown as "No data", never "Operational"; the overall status is the worst status among components with data. Incidents appear automatically with a generic title; public updates are a distinct incident event type. The page polls every 60 s and never uses Reverb.
**Why:** A public surface must not leak tenant data or internal topology, must stay cheap under load and must not present missing data as health.

## ADR-023 — Custom status page domains
**Decision:** A status page may have one custom domain, proven by a `_veyra-challenge.<domain>` TXT record (`veyra-verification=<token>`, token renewed whenever the domain changes). `veyra:status-domains:verify` (hourly) retries pending domains for about a week and re-checks verified ones daily; three consecutive failures revoke a verified domain. A global middleware serves only the status page on `/` for a verified, published domain (all other paths 404, before any session starts); every other host, including the `APP_URL` host, IPs and `localhost`, is untouched. The instance host and its subdomains, IP literals and local suffixes are refused. TLS is delegated to the reverse proxy; `/status-domains/tls-check` is the on-demand "ask" endpoint (Caddy example for Docker, manual aliases for Vito).
**Why:** Domain ownership must be proven and re-proven (domain hand-over), the application must never be reachable through a customer-controlled host name, and certificates must not be issued for arbitrary domains pointed at the server.

## ADR-024 — Monitor types behind one probe contract
**Decision:** `monitors.type` is `http`, `tcp` or `heartbeat`. Every type uses the same outbox, `monitor_checks` history, confirmed-state machine, incidents, notifications and statistics; only the probe (`MonitorProbe`, resolved by `ProbeRegistry`) and a type-specific configuration table differ (`monitor_http_configs` today, one table per new type). The relay dispatches `ExecuteProbe`; `ExecuteHttpProbe` remained as a deprecated subclass (removed in 1.3) so jobs serialized by 1.1 still run after an upgrade (removed in 1.3). A type without a probe, or a monitor without its configuration, has its dispatch `skipped` and records no check (UNKNOWN, never DOWN). Confirmation thresholds are resolved per type: HTTP/TCP use `VEYRA_DOWN_AFTER_FAILURES`/`VEYRA_UP_AFTER_SUCCESSES` (3/2); heartbeats use `VEYRA_HEARTBEAT_DOWN_AFTER_MISSES`/`VEYRA_HEARTBEAT_UP_AFTER_PINGS` (1/1), because a missed ping is only recorded once its grace period has elapsed.
**Why:** New check kinds must inherit the reliability guarantees (idempotency, ordering, "missing data is UNKNOWN") instead of re-implementing them, and an hourly cron job must not take three hours to be reported down.

## ADR-025 — Heartbeat monitors: pings through the regular check pipeline
**Decision:** A heartbeat monitor has a secret ping URL `/ping/{token}` (and `/ping/{token}/fail`), accepting GET, POST and HEAD outside the `web` middleware group (no session, cookies or CSRF, body never read), rate-limited to 30/min per token and 600/min per IP. The token is 40 random alphanumeric characters; only its SHA-256 hash is stored, the plain URL is flashed once on creation or regeneration (regeneration invalidates the previous URL). The period (`interval_seconds`, 1 min to 1 week; the column is widened to `INT UNSIGNED`) plus a grace time (1 min to 24 h) define the deadline `last ping + period + grace`, stored in `next_check_at`. A ping is recorded as a check through a `ping` dispatch and `RecordProbeResult` (same idempotency, maintenance flag and state machine) only when it carries information: first successful ping of the period (since the streak start), first ping after a failure, or a `/fail` signal (`heartbeat_failed`); other pings only move the deadline. Heartbeats confirm on one result (ADR-024). Pings of paused monitors are answered 200 and ignored; unknown tokens and deleted monitors get 404. Heartbeats cannot be checked manually.
**Missed deadlines:** the outbox claims a heartbeat when `next_check_at` (the deadline) is due; `HeartbeatProbe` evaluates the window `(deadline − period − grace, deadline]`. A ping in that window (one that arrived after the slot was claimed) skips the dispatch. Otherwise a `heartbeat_missed` failure is recorded **only** if the durable scheduler beat log (`scheduler_beats`, one row per minute in MariaDB, kept 9 days) covers the whole window with no gap above 180 s, edges included; if not, the dispatch is skipped and no check is written. After a miss the next deadline is one period later. Stale detection allows `2 × period + grace + 120 s` for heartbeats. Residual risk: an outage of the web tier alone (pings rejected while the scheduler runs) is indistinguishable from a missed ping; operators should monitor the Veyra URL externally.
**Why:** Pings must inherit the reliability guarantees of probes instead of a parallel state path; about one check per period keeps uptime and coverage comparable with probed monitors; a leaked database must not reveal working ping URLs, and cron jobs must never be broken by a paused monitor.

## ADR-026 — TLS certificate expiry warnings
**Decision:** When an HTTP monitor's target is `https`, the probe enables `CURLOPT_CERTINFO` on the first hop to the monitored host (never on redirect targets on other hosts) and parses the leaf certificate (SHA-256 fingerprint, subject CN, issuer O/CN, `notBefore`/`notAfter`); parsing failures never affect the check result. `monitor_tls_certificates` keeps one row per monitor (public data only), rewritten only when the fingerprint changes or the last confirmation is older than one hour. `veyra:certificates:check` (hourly, one server) raises for each enabled HTTP monitor only the most urgent threshold reached (`VEYRA_CERTIFICATE_WARNING_DAYS`, default `14,7,1`, plus 0 = expired): a certificate first seen 5 days before expiry gets the 7-day warning only. `tls_certificate_alerts` is unique per (monitor, fingerprint, threshold), so each warning is sent once per certificate and a renewed certificate starts over. `notification_deliveries` now belongs to either an incident or a certificate alert (`incident_id` nullable, `certificate_alert_id` added, a CHECK constraint enforces exactly one), unique per (alert, channel); deliveries go to the monitor's enabled channels of the same organization through the existing `SendNotificationDelivery` job (events `certificate_expiring` / `certificate_expired`). Alerts are purged after the delivery retention period (90 days), cascading to their deliveries. An expired certificate does not open an incident by itself: the HTTPS check already fails on TLS verification.
**Why:** Certificate expiry is the most common avoidable HTTPS outage; warnings must reuse the delivery pipeline (retries, history, idempotency) without faking incidents, and must not spam channels every hour or every check.

## ADR-027 — Organization language
**Decision:** Each organization has a `locale` (`organizations.locale`, `varchar(10)`, default `en`) chosen among `config('veyra.locales')` (English and French in 1.3), editable by Owners and Admins. The language of a request is resolved server-side: `SetRequestLocale` (web group) negotiates `Accept-Language` on the primary subtag (falling back to `APP_LOCALE`, then English) for pages outside an organization; `ResolveOrganization` then applies the organization language on `/o/{slug}` routes; public status pages (path or custom domain) always use the owning organization's language, never the visitor's, so the shared 30 s HTTP cache stays correct, and their snapshot cache is keyed per language. A new organization takes the language of the request that creates it. Notifications carry the organization language in `NotificationMessage::$locale` and render with it explicitly (mail `locale()`, `__()` with a locale argument), independently of the worker process locale; invitations use `Notification::locale()`. The English source strings are the translation keys: `lang/fr.json` is shared by PHP and Vue (`resources/js/lib/i18n.ts`, `t()`/`tc()` with Laravel-style `:name` replacements, bundled dictionaries, no new dependency), and framework messages live in `lang/fr/*.php`. The locale is shared as the `locale` Inertia prop and in `<html lang>`; the client switches on `beforeUpdate` so a page never renders half-translated. Dates and numbers are formatted with the active locale. Data and logs stay in English, the source language: incident causes are stored in English and translated when displayed (`ProbeErrorCode::translateCause()`), and framework-independent domain exceptions (`DestinationRejected`, `InvalidExpectedStatuses`) keep an English `getMessage()` plus a `translatedMessage()` used by validation (`TranslatableMessage`). Internal delivery errors stay in English. Coverage tests (Pest and Vitest) fail when a `t()`/`__()` literal or an enum label has no French translation.
**Why:** The organization is the unit that owns monitors, public pages and alert channels, so one setting gives a consistent language to members, visitors and recipients. Server-side resolution keeps `<html lang>`, validation messages, flashes and e-mails consistent with the UI. A per-user override can be added later without changing this model.

## ADR-028 — Landing page on the root URL
**Decision:** `/` is served by `HomeController`: signed-in users are redirected to `/dashboard` (unchanged behaviour); guests see the public landing page (`Welcome`, no layout, translated, browser language) only when `VEYRA_LANDING_PAGE=true`, and are redirected to `/login` otherwise. The flag defaults to `false`. The landing page is part of the application, not a separate site, and only receives `canRegister` (public registration open) and the source URL; sign-up calls to action disappear when registration is closed.
**Why:** One codebase serves both the Veyra site and self-hosted Community instances: operators must not advertise Veyra to their own visitors by default, while the public instance gets a landing page with no extra deployment.


## ADR-029 — Organization entitlements
**Decision:** The first entitlements contract announced by ADR-011. `App\Domain\Entitlements\Contracts\Entitlements::limit(Organization, Feature): ?int` returns the limit of a feature for an organization, `null` meaning unlimited (or, for value features, the instance default). The Community core binds `CommunityEntitlements`, which limits nothing; an optional extension (e.g. `extensions/cloud`) rebinds the contract in its own service provider. Core code never tests the edition to decide a limit. Features: counted ones, `Monitors` (**active** monitors only: paused monitors cost no probes, and a downgrade can pause the excess), `Members` (members plus pending invitations), `StatusPages`, `CustomDomains`, `NotificationChannels`; value ones, `MinIntervalSeconds` (probed HTTP/TCP monitors; heartbeat periods are passive and not restricted) and `CheckRetentionDays` (raw checks; daily aggregates are unaffected). `Quota` is the single entry point used by the Actions: `ensureCanAdd()` must run inside the transaction that adds the resource; it locks the `organizations` row (`SELECT … FOR UPDATE`) before counting, so concurrent additions are serialized, and throws `LimitReached`. Points of enforcement: monitor creation and resume (pausing is always allowed), invitation (re-sending the invitation of the same e-mail is not an addition) and acceptance (refused when the limit was lowered since), status page creation, adding a domain to a page without one (replacing or removing never counts), notification channel creation, the minimum interval in `SaveMonitorRequest` (an edited monitor may keep an interval below a lowered minimum, not go further below it) and per-organization retention in `PurgeExpiredHistory`. **Limits apply to growth only:** nothing is deleted or paused when a limit is lowered; resources above it are kept and nothing more can be added. `LimitReached` keeps an English message and is rendered as a `limit` validation error plus an error toast (`errors.invitation` on acceptance). The interface receives `currentOrganization.limits` with the usage of limited counted features only (empty on Community, so nothing is shown and no query runs). `veyra:doctor` fails when `VEYRA_EDITION=cloud` runs with the Community entitlements.
**Why:** Cloud plans need limits, but the Community core must stay unlimited and independent of commercial code. Locking the organization row makes limits exact under concurrency without counters to keep in sync, and "growth only" keeps limit changes (downgrades, unpaid invoices) free of data loss; how to handle an organization above its limits is the extension's policy.

## ADR-030 — Optional extensions
**Decision:** An optional extension (the commercial Cloud extension first) lives in its own repository and is installed as a Composer package with its own service provider (Laravel package discovery); its sources are cloned into `extensions/<name>/`, ignored by git and by the Docker context, so Community images and this repository never contain extension code. Dependencies only go one way: the extension depends on the core, never the reverse, and the core works identically when `extensions/` is empty or absent. The core offers explicit, tested extension points only: **pages** (`resources/js/lib/pages.ts` adds `extensions/*/resources/js/pages/**/*.vue` to the Inertia resolver under the same naming as core pages, conventionally prefixed with the extension name such as `cloud/billing/Show`; a core page always wins over an extension page of the same name; `config/inertia.php` adds the extension page directories for `assertInertia`); **translations** (`extensions/*/lang/*.json` merged into the client dictionaries, core entries winning; PHP translations are loaded by the extension with `loadJsonTranslationsFrom`); **styles and tooling** (Tailwind `@source` on `extensions/*/resources`, `tsconfig`, Vitest cover `extensions/*`); **Content Security Policy** (`veyra.csp.script_src`, `frame_src`, `img_src` and `connect_src` accept extra origins set by an extension's provider, empty by default; values with separators or quotes are dropped so configuration cannot inject a directive); **navigation** (`OrganizationNavigation::add()` from the extension's provider: an id, an English title translated per request, a named route taking the organization, an optional ability checked against it and one of a few known icons; shared as `currentOrganization.navigation` and shown before "Settings"); **entitlements** (rebinding `Entitlements`, ADR-029); the **`OrganizationDeleting`** event, dispatched synchronously inside the deletion transaction while the organization's rows still exist (listeners may throw to abort; external clean-up must be queued after commit); and the **`RaiseMonitorIntervals`** action, which raises probed monitors (paused ones included, heartbeats excluded) below a minimum to the shortest selectable interval at or above it, keeping their next check time. A **user menu** (`UserNavigation::add()`, Sprint 10c) takes the same arguments except that the named route has no parameters and the ability is checked for the user alone, without an organization; entries are shared as `auth.navigation` on every authenticated page, inside or outside an organization, and shown in the user menu between "Settings" and "Log out". Both registries share one closed icon list (`OrganizationNavigation::ICONS`, now including `shield`, mapped in `resources/js/lib/extension-icons.ts`). **Instance administrators** are the verified users listed in `VEYRA_ADMIN_EMAILS` (case-insensitive, `User::isInstanceAdministrator()`), exposed as the core ability `administerInstance`; `viewHorizon` is defined from it, so there is one rule. It is never an organization role, and the core grants it no cross-organization access: an extension that offers operator pages gates them with this ability and owns their audit. Account deletion now deletes sole-member organizations through `DeleteOrganization`, so listeners run and monitoring history is purged (previously it was left behind).
**Why:** The hosted service needs pages, navigation and lifecycle hooks, but the AGPL core must stay complete and free of commercial code, and Community users must not pay for hooks they do not use. A handful of narrow, documented extension points is easier to keep stable and to test than a general plugin system.

## ADR-031 — Operator access across organizations
**Decision:** Access across organizations exists only in optional extensions (the Cloud operator console first), never in the core, and follows one policy: routes outside `/o/{slug}` and outside `ResolveOrganization`, reachable only with the core `administerInstance` ability (verified users listed in `VEYRA_ADMIN_EMAILS`), answering 404 to anyone else; a recent password confirmation (`password.confirm`) on every page; throttled writes; a mandatory reason for every change, recorded in the same transaction with the state before and after in an append-only audit that outlives the organization and the operator; metadata and counters only, never tenant content (monitor URLs and headers, notification channels, status page content); no impersonation (amended by ADR-038). Plan changes made by an operator go through the extension's entitlements and the core's existing actions (`SetMonitorEnabled`, `RaiseMonitorIntervals`), so the core needs no suspended state. Two-factor authentication for operators is not available yet (Fortify's feature is not enabled in the core) and is a separate decision.
**Why:** The hosted service needs support and abuse handling without database access, but every cross-tenant read or write is a tenancy exception: keeping it out of the core, behind a single rule, disclosed to nobody else and fully audited keeps that exception small and reviewable, while Community instances keep no such surface.

## ADR-032 — Public site links
**Decision:** A third navigation registry, `PublicNavigation::add(id, title, route, placement)`, lets an optional extension link public pages it serves itself (the hosted service's pricing, terms of service, privacy and refund policies first). The route is named, takes no parameters and must be reachable by guests; the title is an English source string translated per request; the placement is `header` (landing page navigation) or `footer` (footers of the landing, authentication and application pages). Links carry no ability: they are the same for everyone. They are shared as `publicNavigation` on every page of the `web` group, never on public status pages (their sessionless stack shares nothing, ADR-022), so a customer's status page never advertises the hosted service. The pages themselves, their routes and their content belong to the extension; an extension page that must not use the application layout declares its own layout (`defineOptions({ layout })`), which Inertia applies before the core's default. Community shares an empty list and renders nothing.
**Why:** The hosted service needs public commercial and legal pages (Paddle requires them to be linked from the site), but the AGPL core must neither contain commercial content nor advertise Veyra on self-hosted instances (ADR-028). One narrow, link-only extension point keeps both true without a page or layout system in the core.

## ADR-033 — Outgoing webhooks
**Decision:** A third notification channel type, `webhook`, POSTs a versioned JSON payload (`version: 1`) for every notification event (`incident.opened|acknowledged|reminder|resolved`, `certificate.expiring|expired`, `test`) to a URL chosen by the organization. Payloads carry identifiers, names, timestamps (UTC ISO 8601) and the English incident cause; only `title` and `summary` follow the organization language. They never contain the monitored URL or host, request headers, recipients or secrets. Deliveries are signed with the [Standard Webhooks](https://www.standardwebhooks.com/) scheme (`webhook-id`, `webhook-timestamp`, `webhook-signature: v1,…` = HMAC-SHA256 over `id.timestamp.body`); `webhook-id` is the delivery row id, stable across retries, so receivers can drop duplicates. The `whsec_` secret is generated by the server, stored encrypted with the channel configuration, flashed once after creation or regeneration and never sent to the browser again. The URL goes through the probe SSRF policy (`DestinationGuard`: allowed ports, host name rules, every DNS answer) when saved and before each send, and the connection is pinned to the validated IP (`PinnedConnection`, shared with HTTP probes); redirects are not followed, proxies are ignored, the timeout is 5 s and the response body is ignored and capped at 64 KiB. HTTPS is required, except on instances that allow private networks (never the cloud edition). Retries and idempotence are those of ADR-017: 2xx is sent; 408, 429 (with `Retry-After`), 5xx, timeouts, connection and DNS failures are retried; other statuses, redirects and rejected destinations fail permanently. Webhook channels count towards the existing notification channel limit.
**Why:** E-mail and Discord do not cover incident tools (PagerDuty, Opsgenie), automation (n8n, Zapier) or in-house scripts, and a public API stays deferred. A standard signature scheme lets receivers use existing libraries instead of a Veyra-specific format. A user-chosen URL is an SSRF vector from the notification workers, so it gets exactly the protections of probes rather than a weaker copy.

## ADR-034 — Slack channel
**Decision:** A `slack` notification channel type posts to Slack incoming webhooks. Like Discord (and unlike ADR-033 webhooks), the destination is fixed: only `https://hooks.slack.com/services/T…/B…/{token}` is accepted, re-validated before each send; Workflow Builder `/triggers/` URLs are refused because they expect another payload. The URL is a secret: stored encrypted, never returned to the browser, summarized as "…abcd". Requests use a 5 s timeout, no redirects and no proxy. The message is Block Kit inside a legacy attachment, for the event colour: top-level `text` (push fallback), title, summary, fields (monitor, cause, duration, certificate expiry and issuer), the organization name and an "Open in Veyra" button, in the organization language (ADR-027). Every untrusted value is mrkdwn-escaped (`&`, `<`, `>`). Retries follow ADR-017: 2xx is sent; 429 (`Retry-After`, 30 s by default, at most 1 h), 5xx and connection failures are retried; other statuses fail permanently. Slack's plain-text error code is copied into the delivery error only when it is a short `[a-z_]` code. Slack channels count towards the notification channel limit.
**Why:** Slack is the team chat most often asked for after e-mail; going through the generic webhook would require a translation service. A fixed, allow-listed host needs no probe SSRF policy. Escaping blocks mention and link injection through monitor or organization names, which Slack's webhooks cannot disable otherwise.

## ADR-035 — Visual identity
**Decision:** Veyra's identity is an indigo accent (`oklch(0.51 0.2 275)` light, `oklch(0.68 0.16 275)` dark, `#4f46e5` where only hex works) on cool slate neutrals (hue 265), Inter for text and JetBrains Mono for technical values (URLs, latencies, status codes), served through the existing Bunny Fonts integration. The mark is the pulse glyph (`AppLogoIcon`) knocked out of a rounded square (`AppLogoMark`); the wordmark is the instance name in Inter semibold. All colours are design tokens in `resources/css/app.css` (light and `.dark`). Statuses use dedicated semantic tokens, never raw palette colours or the brand accent: `status-{up,degraded,down,maintenance,unknown}` with `-foreground` (text on the solid colour) and `-soft`/`-soft-foreground` (banners), plus `success` and `warning` text aliases. A status is never conveyed by colour alone: badges and public status labels pair the colour with a distinct icon and a text label, and uptime bars draw missing data as a short hatched stub. Every text/background pair meets WCAG AA (4.5:1) and every status colour stands out from the page as a graphic (3:1), checked by `resources/js/lib/contrast.test.ts`, which parses the CSS. Public status pages use only the neutral and status tokens (no indigo, no Veyra logo in the header, the version footer only), so customer branding (sprint 14) does not compete with Veyra's. E-mails keep Laravel's markdown layout with an overridden theme and header (`resources/views/vendor/mail/html/`): indigo button and links, slate text, a CSS-only mark and no remote image.
**Why:** The default shadcn theme gave Veyra no recognisable look, and status colours were hard-coded Tailwind classes in two dozen files, with no contrast guarantee and red/green as the only cue. Semantic tokens make the palette changeable in one place and testable; keeping the brand hue away from the status hues stops the accent from reading as "up". Status pages belong to the customer's brand more than to Veyra's.

## ADR-036 — Status page audience: branding, subscriptions, feeds and badges
**Decision:** Status pages gain an audience while keeping ADR-022's whitelist and sessionless model. *Branding:* an optional accent colour (`#rrggbb`) and a logo and favicon. Images are validated from their bytes (signature, minimal structure, `getimagesizefromstring()`, no GD dependency): PNG/JPEG/WebP for the logo (≤ 256 KB, ≤ 2000 px), PNG/ICO/WebP for the favicon (≤ 64 KB, ≤ 512 px), never SVG. They are stored as `MEDIUMBLOB` in `status_page_assets`, so there is no shared volume to provision and the database backups cover them. They are served at `/status/{slug}/assets/{kind}-{hash16}.{ext}` with `Cache-Control: immutable`, `nosniff`, `CSP: default-src 'none'; sandbox` and no cookies. `AccentColor` picks black or white text on the accent; the accent is used as a text colour only on the backgrounds (light, dark) where it reaches 4.5:1, otherwise links keep the neutral colour. *Subscriptions:* visitors subscribe by e-mail when a page enables it (`subscriptions_enabled`). The flow is double opt-in: the POST answers the same way for new, pending and confirmed addresses (no enumeration), uses a honeypot, and is limited to 5/h per IP and 100/h per page. Confirmations are resent at most every 10 min. Addresses are encrypted at rest, looked up by an HMAC (unique per page), never shown (managers see counts only) and never queued or logged (jobs carry ids). Confirmation (48 h) and unsubscribe (permanent) links are Laravel signed URLs on the instance host. Their GET only shows a button, so link scanners change nothing, and the unsubscribe POST also serves RFC 8058 one-click (`List-Unsubscribe`, `List-Unsubscribe-Post`). Unconfirmed rows are purged after 7 days. Subscribers receive incident openings, public updates, resolutions and maintenance creation, but not edits. Each one creates a `status_page_announcements` row per published, subscribed page showing an affected monitor (unique `(page, subject, event)`), with a payload frozen from public fields only. `SendStatusPageAnnouncement` then fans it out in batches of 500 to subscribers confirmed before the announcement (unique `(announcement, subscriber)` deliveries), and `SendSubscriberAnnouncement` sends each e-mail with retries. Announcements and deliveries are kept 30 days. *Feeds and badges:* Atom and RSS feeds (`/feed.atom`, `/feed.rss`, 5 min public cache) and SVG badges (`/badges/{component}/status.svg` and `uptime-{24h,7d,30d}.svg`, 60 s) are rendered from the cached snapshot, in the organization language. Unknown components, other pages' components, unpublished pages and uptime badges of pages hiding uptime all return 404. *Custom domains* (ADR-023) serve an explicit list of paths: `/`, the feeds, badges, assets and `POST /subscribe`; everything else stays 404. *Entitlements* (ADR-029): `StatusPageSubscribers` (counted per organization, pending included) and `StatusPageBranding` (value feature, `0` = off). A visitor over the limit gets a neutral "not available" answer. Existing branding is kept when the feature is removed, and new branding is refused. Community limits nothing.
**Why:** Customers want their users to follow incidents without watching the page, and to embed status where their users already are, without Veyra ever leaking more than the public page shows. Storing images in MariaDB keeps both deployment modes identical. Freezing announcement payloads and keying deliveries makes retries and replayed events harmless.

## ADR-037 — Advanced HTTP checks: bodies, basic auth, keyword assertions, latency
**Decision:** HTTP monitors may use POST, PUT and PATCH with a body of at most 16 KiB and a content type from a closed list (JSON validated on save), plus optional basic auth. The body and the credentials are encrypted at rest like custom headers and never leave the server: the UI shows only the body's content type and size and the basic auth user name, and editing keeps them unless the user replaces them (`body_mode`, `auth_mode` = `keep|replace`, as `headers_mode`). They are only sent to the monitored host: a cross-host redirect drops headers, credentials and body and continues as GET; 303, and 301/302 after a body request, continue as GET without body (browser behaviour); 307/308 keep them on the same host. A keyword assertion (`contains`/`not_contains`, case option) is evaluated on the body the probe already downloads under its 1 MiB cap, only when the status is expected; the probe asks for `identity` encoding, decodes gzip/deflate under the same cap and reports anything else as `body_unreadable` rather than guessing. Failures get their own codes (`keyword_missing`, `keyword_found`, `body_unreadable`), so incident causes say what failed. A latency threshold flags slower successful checks `slow` on the check row, decided by the probe at record time (changing the threshold never rewrites history). The state machine treats slow checks as successes — they never count towards DOWN and do confirm a recovery — and degrades an otherwise UP monitor after `downAfter` slow checks in a row, leaving DEGRADED after `upAfter` fast ones. An incident is resolved by a success streak of `upAfter`, slow or not.
**Why:** API health endpoints often need a POST, credentials or a body check to be meaningful, and slowness is the first sign of trouble users notice. Reusing the probe's existing body cap, SSRF guard and secret handling adds the features without a new attack surface. Storing the slow flag keeps evaluation deterministic on replay, and reusing the confirmation thresholds keeps one mental model: a single slow response is noise, a streak is a state.

## ADR-038 — Operator impersonation
**Decision:** ADR-031 is amended: an optional extension may let an instance administrator act as another user, with full access to that user's organizations, under the ADR-031 policy (operator routes outside `/o/{slug}`, `administerInstance` or 404, recent password confirmation, throttled, a mandatory reason, an append-only audit owned by the extension). The core gains one extension point and no impersonation code: the `Impersonation` contract (`current(Request): ?array{operator, stopUrl}`), bound to `NoImpersonation` (always `null`) and rebound by the extension, shared as `auth.impersonation` on every authenticated page and rendered by `ImpersonationBanner` at the top of the application layout (the user acted as, the operator's e-mail, a "Stop impersonating" button that POSTs to `stopUrl`). The extension owns starting, stopping, guarding and auditing, and follows these rules: it starts from an organization's member, never for the operator themself, another instance administrator or while already impersonating; it logs the target in on the session guard (no remember-me, regenerated session) and drops the operator's password confirmation, which comes back only when the impersonation stops; it ends after 60 minutes, on stop or on logout; everything the user can do inside organizations is allowed, but account actions (profile, e-mail, password, account deletion, password confirmation) and the operator console are refused while impersonating; the start, the end and every write request (method, route name, route ids, status; never the payload, headers or URL) are audited. The impersonated user is not notified; e-mails triggered during the session (invitations, for instance) go out under their name. Policies, `ResolveOrganization` and Reverb channel authorization need no change: the operator is the user for the length of the session. Community instances keep no impersonation at all.
**Why:** Support on the hosted service needs to see and fix what a customer sees, which metadata alone cannot do. Keeping the feature in the extension behind ADR-031's single rule, with account security out of reach and every write audited, keeps the tenancy exception reviewable; a single core contract with a null default keeps the AGPL core free of it.

## ADR-039 — ntfy, Gotify, Telegram, Microsoft Teams and PagerDuty channels
**Decision:** Five notification channel types join e-mail, Discord, Slack and webhooks, on the same pipeline (ADR-017 delivery rows, retries and idempotence) and the same rules: configuration encrypted in `config_encrypted`, managed by Admins/Owners, never returned to the browser (summaries show a host, a topic, a chat id or the last four characters), counted towards the notification channel limit, text in the organization language (ADR-027), 5 s timeouts, no redirects, no proxy, errors that never contain a URL or a token. Responses are classified once (`ResponseClassifier`): 2xx is sent; 408, 429 (`Retry-After`, 30 s by default, at most 1 h) and 5xx are retried with connection failures; redirects and other statuses fail permanently; a provider message is copied into the error only when it is short plain text that does not echo the channel secret.
- **ntfy** and **Gotify** target a server chosen by the organization (ntfy.sh or self-hosted), so the URL gets the probe SSRF policy of ADR-033 when saved and before each send (`WebhookDestination`, connection pinned to the validated IP, response capped at 64 KiB; plain HTTP and private networks only when the instance allows them, never on the cloud edition). ntfy takes a topic URL (`https://server[/prefix]/topic`) and publishes JSON to the server root with an optional Bearer access token; Gotify takes a server URL and posts to `/message` with the application token in `X-Gotify-Key`. Both are plain text, so nothing needs escaping; priorities follow the event.
- **Telegram** uses the fixed `https://api.telegram.org/bot{token}/sendMessage` with a validated bot token and chat id (numeric or `@channel`). Messages use HTML mode with every untrusted value entity-escaped; a message that would exceed 4096 characters is sent as plain text rather than cut inside markup. `parameters.retry_after` is honoured on 429.
- **Microsoft Teams** accepts only Power Automate workflow URLs (`https`, hosts ending in `.logic.azure.com` or `.api.powerplatform.com`, a `/workflows/` path), re-validated before each send; retired Office 365 connector URLs are refused. The Adaptive Card renders untrusted values with `TextRun` elements, which Teams never parses as Markdown.
- **PagerDuty** uses the fixed Events API v2 endpoint with a 32-character routing key. A Veyra incident is one PagerDuty alert keyed `veyra-incident-{id}`: opening triggers it, acknowledgement acknowledges it, recovery resolves it; retries and replays reuse the key. Reminders are never queued for PagerDuty channels (it runs its own escalations). A trigger or acknowledgement sent after the incident was resolved is skipped (failed with an explicit reason) so a late retry cannot open an alert nothing resolves. Certificate warnings trigger an alert keyed by their delivery; a test triggers then resolves a throwaway alert.

**Why:** These are the channels most requested by self-hosters (ntfy, Gotify), small teams (Telegram) and companies (Teams, PagerDuty). Fixed hosts keep the SSRF surface at the allow-list level; the self-hosted servers reuse the existing probe policy instead of a second one. Mapping incidents onto PagerDuty's dedup key lets PagerDuty own on-call escalation without duplicate pages.

## ADR-040 — Two-factor authentication
**Decision:** ADR-007 is amended: Fortify's `twoFactorAuthentication` feature is enabled with `confirm` (a secret only counts once a code from the app was confirmed) and `confirmPassword` (enabling, confirming, regenerating recovery codes and disabling require a recent password confirmation, like the security page itself). Secrets and the 8 recovery codes are stored encrypted by Fortify on `users` and hidden from serialization; the QR code and setup key are shown only until confirmation, and the recovery codes only right after confirmation or regeneration. Sign-in asks for a TOTP code or a single-use recovery code (`/two-factor-challenge`, 5 attempts per minute per pending login). An Owner can require two-factor authentication for an organization (`organizations.require_two_factor`, Owners only, and only once their own second factor is confirmed). `EnsureOrganizationTwoFactor` runs after `ResolveOrganization`: a member without a confirmed second factor is redirected to the security settings with an explanation, on every organization route (reads and writes) except leaving the organization; non-members still get a 404; the member's other organizations are unaffected. The private Reverb channel of such an organization is refused the same way. Nothing is deleted or logged out: access comes back as soon as the second factor is confirmed. Requiring two-factor authentication for instance operators (ADR-031) remains a separate decision; operators can now enable it on their own accounts.

**Why:** Monitoring accounts can change alert routing and status pages, so a stolen password is enough to hide an outage; TOTP with recovery codes is the most portable second factor and Fortify already ships it. Enforcing it per organization, at the tenant middleware and the channel, keeps one rule for HTTP and real time without a global switch that would lock self-hosted administrators out.
